# 02 — 功能开关设计与播报文案规则

> 上级文档：[../../CLAUDE.md](../../CLAUDE.md)。架构见 [01-architecture.md](01-architecture.md)，TTS 见 [04-tts.md](04-tts.md)。

## 第一层：播报开关（7 项，独立勾选）

勾选即播报**事件模板播报**（所谓「原文」指按事件类型的固定模板，非平台原始数据）。与 UI 截图一一对应：

- [ ] 弹幕
- [ ] 礼物投喂
- [ ] 醒目留言
- [ ] 进场消息
- [ ] 关注通知
- [ ] 大航海上舰
- [ ] 点赞

## 第二层：附加感谢播报开关（4 项，独立可选）

与第一层**解耦**，可单独开启/关闭：

1. 礼物投喂感谢播报
2. 醒目留言感谢播报
3. 关注通知感谢播报
4. 大航海上舰感谢播报

> 第一层播原文、第二层播感谢语，两层互不依赖（例如：只开「礼物投喂感谢」不开「礼物投喂」时，礼物事件仍应触发感谢播报）。

## 独立可选开关：舰长进场播报

勾选启用后，舰长用户进入直播间时播报：`欢迎[用户昵称]进入直播间`

## 事件模板播报文案（第一层）

| 事件 | 播报文案 |
|------|----------|
| 弹幕 | `[用户昵称]说：[弹幕内容]`（内容加引号朗读） |
| 礼物投喂 | `[用户昵称]投喂了 [数量] 个[礼物名称]` |
| 醒目留言 | `[用户昵称]发来醒目留言：[留言内容]` |
| 进场消息 | `[用户昵称]进入直播间` |
| 关注通知 | `[用户昵称]关注了直播间` |
| 大航海上舰 | `[用户昵称]开通了[舰长/提督/总督]` |
| 点赞 | `[用户昵称]点了赞` |

## 播报队列规则（强制）

1. **全局队列顺序播报**：所有播报文本进入统一队列，一条读完才读下一条，禁止并行/跳过。
2. **原文与感谢成对**：同一事件产生的「模板播报 + 感谢播报」作为一个播报单元入队，原文读完紧接着读感谢，中间不被其他事件插队。
3. **付费事件优先（插队）**：礼物投喂、大航海上舰、醒目留言（花钱的事件）入队时排到普通事件（弹幕/进场/关注/点赞）之前。
4. **绝不打断正在播报的条目**：优先级只影响队列中等待条目的顺序；当前正在播报的必须读完，即使是付费事件也只入队等待。

## 播报文案规则（第二层：感谢）

金额阈值在 UI 设置中提供输入框，用户可自定义，**默认 50 元**。

| 触发 | 文案 |
|------|------|
| 礼物投喂感谢 | `感谢[用户昵称]投喂的 [数量] 个[礼物名称]`；礼物金额 ≥ 阈值时追加播报「老板大气」 |
| 大航海上舰感谢 | `感谢[用户昵称]的舰长，老板大气`（固定追加） |
| 醒目留言感谢 | `感谢[用户昵称]的醒目留言`；留言金额 ≥ 阈值时追加播报「老板大气」 |
| 关注通知感谢 | `感谢[用户昵称]的关注` |
| 舰长进场 | `欢迎[用户昵称]进入直播间` |

## 实现约束

- 所有开关状态与金额阈值持久化到用户配置文件（见 [03-config-secrets.md](03-config-secrets.md)）。
- 文案生成集中在 `core/broadcaster.py`，纯函数实现，便于第二阶段移植（见 [01-architecture.md](01-architecture.md)）。
- 修改开关行为或文案规则时，**必须同步更新本文件**。
